# ADR-010: Automation and prod jobs run as service principals

- **Decision:** automation never uses a personal access token. Two Databricks service principals log in with OAuth (client ID and secret): `corvella-ci` for CI on pull requests, with access only to `corvella_dev`; and `corvella-deployer` for CD on merge to `main`, which deploys the `prod` target and is the `run_as` identity of every prod job, with access to `corvella_prod`. Catalog and schema grants are defined in the bundle; warehouse access and the right to create catalogs are set once by an admin. The deployer's credentials are stored in a GitHub environment `prod` restricted to the `main` branch, so only the CD workflow can read them.
- **Context:** CI runs the code of a pull request before it is reviewed or merged, so any credential CI holds is available to unreviewed code. Personal tokens expire and carry all of their owner's permissions, and jobs that run as a person break when that person leaves. Free Edition allows creating service principals.
- **Alternatives considered:** a personal access token for CI and CD (simplest, but tied to one person, expires, and gives automation full personal access); one service principal for both CI and CD (fewer secrets, but any pull request could write to prod before review).
- **Consequences:** prod changes only through reviewed code merged to `main`, enforced by permissions rather than convention; prod jobs run under a stable identity with only the access they need; OAuth tokens are short-lived and renewed automatically. Two principals and their secrets must be maintained, and a new permission for a prod job must be granted to `corvella-deployer` in the bundle.
