# ADR-008: Jobs defined as code with Databricks Asset Bundles

- **Decision:** all Databricks jobs are defined in a Databricks Asset Bundle (`databricks.yml` and `resources/*.yml` in the repository) and created or updated with `databricks bundle deploy`. Each task runs the copy of the code that the deploy uploads to the workspace, not a Git clone. Workspace-specific values are bundle variables (for example, the SQL warehouse is found by name with a `lookup`), and the host and token come from the environment, never from the bundle files. Every job name starts with its target (`[dev] …`, `[prod] …`), and schedules are paused with the `trigger_pause_status` preset; the `dev` target doesn't use development mode, which would also prefix every schema with the developer's name (see ADR-009).
- **Context:** the pipeline needs three jobs (source simulator, ingestion, transformation) in a dev and a prod environment, reviewed through pull requests and rebuildable at any time. Jobs created in the UI can't be reviewed or reproduced, and their settings drift. A smoke test on Nov 9, 2026 confirmed in Free Edition that a bundle validates, deploys and runs a dbt task on serverless compute, with the warehouse found by name.
- **Alternatives considered:** jobs created by hand in the UI (fast to start, but not versioned or reviewable; kept only as a reference export of the first smoke test job); jobs with a Git source created through the Jobs API (each run clones `main`, but job settings still live outside the repository and need custom scripts to manage).
- **Consequences:** jobs, their schedules and their dependencies are versioned and reviewed like code; what runs is what was last deployed, so deployment must follow merges (manually now, from GitHub Actions later). Developers need the Databricks CLI. The bundle also defines the schemas and volumes; the catalogs themselves are created once with SQL, because bundles can't create catalogs on Free Edition's Default Storage (see ADR-009).
