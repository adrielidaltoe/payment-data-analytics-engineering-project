# ADR-011: One repository for pipeline code and dbt

- **Decision:** the Python pipeline code (`src/corvella/`: source data generator, replay and ingestion), the dbt project (`dbt/`), the bundle (`databricks.yml`, `resources/`) and the CI/CD workflows live in one repository. Inside it the two code bases stay independent: separate folders, separate dependency groups in `pyproject.toml`, separate linters (ruff for Python, sqlfluff for dbt SQL), and dbt never imports the Python package. The repository is split when ownership splits (see Consequences).
- **Context:** the Python code and the dbt project are two halves of one pipeline, not two products. Ingestion writes the bronze tables and dbt reads them, so the bronze schema is a contract between them, and a typical change touches both sides (for example, a new source column changes the generator, the ingestion config and the dbt staging model and tests). The bundle deploys the ingestion and transformation jobs together, and the ingestion job triggers the dbt job (ADR-008). Environments, catalogs, service principals and secrets are shared (ADR-009, ADR-010). The project has one owner and one release cycle.
- **Alternatives considered:** one repository for the Python code and one for dbt (clear ownership boundaries and independent releases, but a cross-cutting change needs two coordinated pull requests and a merge order, `main` of one can expect a column the other doesn't produce yet, and the bundle, CI/CD, environments and secrets must be duplicated or a third repository must pin versions of both).
- **Consequences:** a change to the contract lands in one pull request, reviewed and tested together, and is deployed as one bundle, so prod always matches one commit on `main`. There is one CI/CD setup and one set of environments to maintain. CI must avoid running checks a change doesn't need, for example `dbt build` only when `dbt/` changes. Revisit this decision if a different team takes ownership of one side, if the ingestion code becomes a library used by other projects, if one side needs access restrictions the other doesn't, or if CI or reviews become slow. Because the boundaries are already clean, splitting is mechanical: move `dbt/` (or `src/`) to its own repository with its share of the workflows and bundle resources.
