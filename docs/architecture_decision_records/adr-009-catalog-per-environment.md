# ADR-009: One catalog per environment, deployed as bundle targets

- **Decision:** two Unity Catalog catalogs, `corvella_dev` and `corvella_prod`, with the same schemas inside each (`landing`, `bronze`, `silver`, `gold`). Each catalog is the data side of the matching Databricks Asset Bundle target (`dev` → `corvella_dev`, `prod` → `corvella_prod`). The two catalogs and their grants are created once by an admin with `setup/catalogs.sql`; the schemas and landing volumes inside them are bundle resources, so deploying a target creates its data structure. The catalog name is a bundle variable passed to every job and to dbt; no code hardcodes an environment. Job names start with the target (`[dev] …`, `[prod] …`). The `dev` target pauses schedules with the `trigger_pause_status` preset instead of using development mode, because development mode also prefixes every schema with the developer's name (`dev_<user>_bronze`), which would break the identical schemas; the `prod` target is deployed only by CD on merge to `main`, and its schedules stay paused with the `trigger_pause_status` preset until the pipeline is ready.
- **Context:** CI needs a place to test every pull request without touching production data. Free Edition has a single workspace, so environments must be separated inside it. Free Edition stores managed data in Default Storage, and the Unity Catalog API that bundles use to create catalogs fails there ("Metastore storage root URL does not exist"); creating the catalog with SQL works. Free Edition users are workspace admins but not metastore admins, so whoever owns a catalog is the only one who can grant access to it.
- **Alternatives considered:** one catalog with prefixed schemas (`dev_bronze`, `prod_bronze`, …): works, but schema names differ between environments, so code and permissions need extra logic; separate workspaces per environment (the usual setup at a real company, not available in Free Edition).
- **Consequences:** dev and prod data never mix; code is identical across environments, only the catalog variable changes; permissions can be granted per catalog. Catalog grants and owners live in a SQL script instead of the bundle, so they are still reviewed like code but applied by hand; `corvella-deployer` owns `corvella_prod`, and the admin grants themselves read access before handing it over. Local development and CI share `corvella_dev`, so a CI run rebuilds the tables being developed against (acceptable for a small team; CI can move to suffixed schemas if it becomes a problem). Both catalogs share the workspace's daily compute quota. Without development mode there is no per-developer isolation inside `corvella_dev`; with more developers, switch `dev` to development mode and pass the prefixed schema names to jobs and dbt. The `corvella` catalog used for the smoke tests is retired. Moving to separate workspaces later only changes the bundle targets.
