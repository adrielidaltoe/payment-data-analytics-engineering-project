# ADR-009: One catalog per environment, deployed as bundle targets

- **Decision:** two Unity Catalog catalogs, `corvella_dev` and `corvella_prod`, with the same schemas inside each (`landing`, `bronze`, `silver`, `gold`). Each catalog is the data side of the matching Databricks Asset Bundle target (`dev` → `corvella_dev`, `prod` → `corvella_prod`). The catalogs, schemas and landing volumes are themselves bundle resources, so deploying a target creates its data structure. The catalog name is a bundle variable passed to every job and to dbt; no code hardcodes an environment. The `dev` target runs in development mode (deployed jobs are prefixed with the user's name and their schedules are paused); the `prod` target is deployed only by CD on merge to `main`, and its schedules stay paused with the `trigger_pause_status` preset until the pipeline is ready.
- **Context:** CI needs a place to test every pull request without touching production data. Free Edition has a single workspace, so environments must be separated inside it. Creating catalogs is allowed in Free Edition.
- **Alternatives considered:** one catalog with prefixed schemas (`dev_bronze`, `prod_bronze`, …): works, but schema names differ between environments, so code and permissions need extra logic; separate workspaces per environment (the usual setup at a real company, not available in Free Edition).
- **Consequences:** dev and prod data never mix; code is identical across environments, only the catalog variable changes; permissions can be granted per catalog. Local development and CI share `corvella_dev`, so a CI run rebuilds the tables being developed against (acceptable for a small team; CI can move to suffixed schemas if it becomes a problem). Both catalogs share the workspace's daily compute quota. The `corvella` catalog used for the smoke tests is retired. Moving to separate workspaces later only changes the bundle targets.
